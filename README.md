# RPG Tracking

一个以**连续个人时间轴**为基础、附带可选 RPG 成长映射的 iOS 时间记录应用。

当前版本：`v3.0.0-beta`

项目状态：重启整理中

## 它要解决什么

这不是番茄钟，也不是为任务分别启动、暂停和停止的普通计时器。

应用首先承认时间始终在流逝，然后由用户为已经过去的时间赋予活动意义：学习、工作、睡眠、吃饭、通勤、休息、游戏，乃至无法回忆的时间，都属于同一条个人时间线。

普通任务计时器通常采用这样的顺序：

```text
选择任务 → 开始计时 → 停止计时 → 生成记录
```

RPG Tracking 的核心顺序是：

```text
时间持续流逝 → 为当前时间段选择活动 → 结算边界 → 下一段立即延续
```

任务不拥有时间。时间先存在，活动名称、分类、评价和经验都是后来附着在时间段上的意义。

## 核心原则

### 1. 时间只有一条

应用面向的是同一个人的唯一现实时间轴，而不是若干可以并行运行的任务秒表。结束当前时间段，也意味着下一段已经从同一时刻开始。

### 2. 记录是对时间的结算

用户不需要先启动某项任务，当前待结算区间会自然地从上一条记录的结束时刻延伸到现在。选择活动的作用是说明这段时间发生了什么，而不是让时间从此刻才开始存在。

### 3. 日常生活与生产活动处于同一层

睡觉、吃饭、卫生间、通勤、做饭、休息和游戏不是计时之外的空白。它们与学习、工作等活动一样，首先都是现实生活中的时间段。

### 4. 评价是可选的上层投影

部分活动可以关联属性、评分、完成结果和奖励倍率，并由此计算经验；日常生活记录不参与属性结算。RPG 系统用于解释和反馈投入，但不决定一段时间是否真实存在。

### 5. 连续不等于假装无所不知

时间可以连续，人的记忆却可能中断。项目后续将把“未记录”作为正式的缺失值类型：承认某段时间已经过去，但无法确定其活动意义，而不是拉长相邻记录或制造数据库空洞。

## 当前实现

### 连续结算主流程

- 计时页进入后，以最新记录的结束时刻作为当前区间起点。
- 当前区间不依赖所选活动，始终延伸到现在。
- 结算生成记录后，下一段立即从同一个结束时刻开始。
- 主线副本与日常生活共用同一套时间记录入口。
- 当前区间显示起止时间、持续时间和当日剩余时间。

### 活动与日常生活

- 主线副本作为可复用的活动与结算模板。
- 日常生活条目只记录时间，不产生属性收益。
- 内置卫生间、睡觉、通勤、吃饭、做饭、休息和游戏预设。
- 支持自定义日常生活条目。
- 支持排序、归档与取消归档；系统预设不可修改或删除。

### RPG 成长映射

- 属性采用“分类 + 条目”两级结构。
- 属性支持累积型与衰退型、基础值、权重和每日衰减参数。
- 主线副本可关联多个属性，并为每项属性设置倍率。
- 结算支持主观评分、未达预期、奖励倍率、地点和备注。
- 历史结算保存属性收益快照；编辑或删除记录后会重新计算受影响属性，避免重复累计。

当前经验公式：

```text
经验 = 基础值 × 属性倍率 × 时间因子 × bonus × 奖励倍率
bonus = 评分 / 100
时间因子 = 分钟 / 60（仅按时间计价时启用）
```

“未达预期”使用设置中的独立 bonus。

### 统计与回顾

- 支持日、周、年和全部范围浏览。
- 显示范围内记录及总经验收益。
- 提供按日汇总经验的历史热力图。
- 支持编辑和删除历史记录。
- 支持紧凑记录布局及热力图方向设置。

### 其他基础设施

- 使用 SwiftData 进行本地持久化。
- 支持简体中文与英文。
- 当前为本地单机应用，不包含账号、同步或云端服务。

## 当前架构

项目目前可以理解为三层：

```text
时间事实层
└── 当前待结算区间、结束时刻、持续时长

活动语义层
└── 主线副本、日常生活、名称、地点、备注

RPG 投影层
└── 属性、评分、倍率、经验、等级与衰退
```

主要数据对象：

- `DungeonLog`：已经结算的时间记录，也是当前统计的基本单位。
- `DungeonTemplate`：带有属性映射的主线活动模板。
- `DailyLifeItem`：不参与 RPG 结算的生活活动类别。
- `DungeonEffectLog`：某条记录产生的属性收益快照。
- `RPGAttribute` / `AttributeGroup`：属性条目及其分类。

## 重启阶段的工程事实

当前版本已经在交互主流程中贯彻“结算后立即延续”的连续时间原则，但连续性还没有完全成为数据模型自身的不可破坏约束：

- `DungeonLog` 当前保存结束时间和整数分钟数，没有独立保存精确起点。
- 起始时间由结束时间和分钟数反推，秒级边界会因取整而丢失。
- 历史记录仍可作为独立对象删除，因此可能产生时间缺口。
- 历史编辑尚不支持在保持总时间守恒的前提下拆分、合并或重分类时间段。
- “未记录”尚未成为正式记录类型。
- 统计目前以记录结束日归属整条记录，尚未处理跨日区间的拆分统计。
- 自动化测试框架已建立，但业务规则测试仍待补充。

因此，当前实现更准确地说是：

```text
连续结算式交互 + 以独立记录保存的时间数据
```

下一阶段的核心不是继续堆叠效率功能，而是让时间连续、区间互斥、总量守恒和显式缺失值进一步下沉到数据模型与编辑规则中。

## 项目定位

RPG Tracking 最初从个人成长与 RPG 数值反馈出发，经过实际使用后，核心逐渐转向连续时间记录。RPG 部分仍然保留，但它现在是建立在时间账本之上的可选解释层。

项目最终关心的不是如何让任务占有更多时间，而是如何把已经流逝的岁月转化为诚实、连续、可认识的个人历史。

## 远景与哲学

以下不是当前版本的功能承诺，而是这个项目可能长期探索的问题。README 不必只承担安装说明的职责；它同样可以记录软件为什么会长成现在这样，以及未来可能往哪里生长。

### 时间第一性，意义第二性

大多数时间管理软件默认先有任务，再由用户为任务启动一只计时器。没有点击开始的时间，仿佛没有进入系统，也不需要交代。

这里采用相反的顺序：时间不因人的意志而启动、暂停或消失。活动、任务、分类、评分和经验都是附着在时间之上的解释。即使用户忘记了某段时间发生了什么，缺失的也只是认识，而不是时间本身。

```text
时间事实 → 活动意义 → 成长解释
```

这也是“未记录”最终应当成为正式记录类型的原因：本体可以连续，记忆允许断裂。软件不应当为了得到一条漂亮的时间线，强行拉长相邻活动或伪造用户已经遗忘的内容。

### 时间账本，而不是任务秒表

这个项目更接近记账软件，只不过它结算的不是金钱，而是人生中唯一、不可增加的时间。

财务账本要求资金来源和去向可以核对；时间账本同样应当要求区间互斥、边界衔接、总量守恒。一天的活动时间与“未记录”时间之和，应当等于这一天实际经过的时间。

活动分类不应无限追求精细。饮食可以继续拆成做饭、外食、聚餐、饮酒，阅读也可以继续拆成每一本书，但分类一旦比记账本身更费力，系统就失去了意义。记录时更适合使用稳定、粗粒度、低判断成本的主活动，例如饮食、睡觉、交通、上课、阅读、工作和休息；具体课程、书籍、地点和情境可以作为本次记录的上下文存在。

原则是：

```text
记录时足够粗，回顾时可以变细；
先让时间得到交代，再逐渐完善对它的解释。
```

### RPG 不是装饰，而是一套现实状态模型

“人生像 RPG”其实说反了。RPG 本来就是从现实中抽取出的模型：角色拥有长期能力，行动消耗短期资源，完成活动带来经验，休息和补给改变当前状态。

```text
Skill / Attribute → 长期能力与属性
Task / Dungeon    → 实际完成的活动
Experience        → 活动带来的长期成长
Focus / Energy    → 专注、精力或体力等短期资源
Time              → 一切行动发生其上的连续世界
```

本项目去除了掉落物、装备、金币等并非必需的游戏层。现实活动本身就是“副本”，活动带来的能力变化就是自然结算，不需要再虚构一件奖励物品证明它有价值。

柳比歇夫式时间记录回答“岁月去了哪里”，RPG 状态模型回答“这些行动怎样改变了人”。两者并不冲突：前者提供不可暂停的现实底板，后者提供理解能力、行动、资源和成长的语言。

### Task、Skill 与统计不应混为一谈

Task 更适合表达现实中主要做了什么，Skill 更适合表达这件事对哪些长期能力产生了影响。同一项活动可能同时作用于多个 Skill；同一个粗粒度 Task 也可能在不同情境下选择不同 Skill。例如“上课”可以保持为稳定的活动入口，而本次记录再说明它是德语课、数学课或其他课程。

这种区分也决定了统计口径：

- 时间统计应当按互斥的活动大类划分，并且总量守恒；时间饼图里更适合出现上课、睡觉、交通和饮食。
- Skill 统计是活动对成长的加权投影，可以重叠，也不必等于现实经过的总时间；它更适合叫作能力贡献、经验来源或等效投入。

因此，Task 回答“时间去了哪里”，Skill 回答“这些时间被解释成了什么成长”。二者可以从同一条记录派生，但不能假装是同一套账。

### 精力是与时间相交的另一套系统

专注度、精力和体力并不适合作为普通 Skill。Skill 描述长期积累的能力；精力更像 RPG 的蓝条或体力条，具有当前值，会被活动消耗，也会通过睡眠、饮食、休息或娱乐得到不同程度的恢复。

```text
时间轴：14:00 ───── 16:00 上课
资源状态：专注度 85% → 61%
成长投影：德语 +1.2，知识 +0.8
```

睡眠也不应当简单地把资源重置为满值。一次被评为 80 分的睡眠，可以表示它只实现了理论恢复效果的 80%；它仍然是连续状态的变化，而不是按下刷新按钮。

这实际上已经足以成为独立软件：时间管理负责记录行动发生的事实，精力管理负责描述短期资源怎样流转，成长系统负责描述长期能力怎样变化。它们平行但相交，共享同一批现实事件，却不应互相吞并。未来若实现这一层，也应作为独立子系统接入时间账本，而不是把全部复杂度塞进每次记录操作。

### 给 RPG 补上时间

游戏很擅长让资源可见：生命值、蓝条、体力、金币、经验和任务进度都拥有清晰的界面。现实世界拥有时间、精力、注意力、体力、知识和恢复能力，却没有默认 HUD；自由度越高，人反而越容易忘记这些资源正在变化。

但传统 RPG 为了好玩，往往又刻意忽略时间：玩家可以暂停，离开副本后的空白不需要解释，睡眠可以瞬间完成，世界只在行动发生时才显得重要。

RPG Tracking 想补上的正是这一层：给 RPG 加上一个不能暂停、不能复制、也不能从头读档的时间世界。游戏模型负责让状态变化可见，时间账本则约束这些数值不能脱离真实生活。

这不是为了假装把人生精确计算成一套游戏规则。现实中的“专注度 62%”终究只是模型，而不是物理测量。更合理的目标是：借用游戏的可见性来理解现实，同时承认估计、模糊、遗忘和无法分类都是现实的一部分。

如果未来的沉浸式 RPG 已经拥有了物理世界、AI 角色和逼真的感官体验，却仍然只是一堆互不相干的任务，也许它缺少的并不是更好的画面，而是给岁月本身建立数据模型。
